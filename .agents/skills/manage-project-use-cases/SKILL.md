# 프로젝트 유스케이스 관리

유스케이스 요청을 소스 코드와 분리하여 `docs/use-cases/`에 보관하고, 구현 근거에 맞춰 상태를 동기화한다.

## 작업 절차

1. 편집 전에 `docs/use-cases/`를 확인한다. `rg --files docs/use-cases`로 인덱스와 관련 가능성이 있는 문서를 찾고 읽는다.
2. 유스케이스를 식별한다.
   - `UC-012`처럼 사용자가 지정한 ID가 있으면 그대로 사용한다.
   - 관련 기능군이 이미 있으면 `UC-012-01`, `UC-012-02`처럼 같은 세 자리 그룹 번호를 공유하는 하위 ID를 할당한다.
   - 새 기능군이면 기존 `UC-NNN` 그룹 중 가장 큰 번호 다음의 세 자리 그룹 번호를 할당하고, 첫 세부 유스케이스는 `UC-NNN-01`로 시작한다.
   - 기존 단일 동작 문서가 이미 `UC-NNN` 형식이면 그대로 유지할 수 있다.
   - ID가 같거나 동일한 동작을 수정하는 요청이면 기존 문서를 갱신한다. 중복 문서를 만들지 않는다.
3. 요청을 받은 같은 작업 차례에 문서를 생성하거나 갱신한다. 구현 요청이 포함된 경우 구현 전에 먼저 문서화한다.
   - 사용자가 유스케이스 변경을 별도로 요청하지 않아도 기능, 버그 수정, 설정, 제약 조건 또는 검증 기준이 기존 유스케이스에 영향을 주면 관련 문서를 자동으로 갱신한다.
   - 기존 유스케이스와 구분되는 별도 목적이나 액터를 가진 기능이면 새 유스케이스를 만들고, 기존 흐름의 변경이면 해당 문서를 수정한다.
4. `docs/use-cases/README.md`에 ID, 제목, 상태, 문서 링크, 갱신일을 반영한다.
5. 사용자가 구현을 요청하거나 명확히 허용한 경우에만 구현 작업을 수행한다.
6. 구현 후 실제 결과를 근거로 유스케이스 상태와 구현 메모를 갱신한다. 마지막에 문서와 코드 변경 사항을 함께 검토한다.

## 문서 형식

파일 이름은 `UC-NNN-short-kebab-title.md` 또는 그룹형 `UC-NNN-MM-short-kebab-title.md` 형식으로 지정하고 다음 구조를 사용한다.

```markdown
# UC-NNN-MM: 제목

- 상태: Proposed
- 마지막 갱신일: YYYY-MM-DD

## 목적

## 액터

## 사전 조건

## 트리거

## 기본 흐름

1. ...

## 대안 및 예외 흐름

- 1a. 기본 흐름 1에서 발생하는 첫 번째 대안 또는 예외를 작성한다.
- 1b. 기본 흐름 1에서 발생하는 두 번째 대안 또는 예외를 작성한다.
- 4a. 기본 흐름 4에서 발생하는 첫 번째 대안 또는 예외를 작성한다.

## 인수 조건

- [ ] ...

## 구현 메모

## 미결 질문
```

문서 내용은 사용자의 언어로 작성한다. 저장소에 이미 정해진 형식이 없다면 위 제목 구조를 일관되게 유지한다.

## 유스케이스 분리 및 번호 규칙

- 유스케이스 문서 하나는 관찰 가능한 한 동작, 한 목적, 한 성공 결과만 다룬다.
- 한 도구나 화면에 여러 동작이 있으면 도구 전체를 하나의 유스케이스로 묶지 말고 동작별 문서로 분리한다.
  - 예: 발판 생성, 발판 간 거리 표시, 선택 발판에서 테스트 시작, 점프 도달 영역 표시를 각각 별도 문서로 작성한다.
- 같은 도구, 같은 기능군, 같은 사용자 워크플로에 속한 문서는 같은 세 자리 그룹 번호를 공유한다.
  - 예: `UC-003-01`, `UC-003-02`, `UC-003-03`은 모두 맵 제작 도구 기능군이다.
- 새 세부 문서를 추가할 때는 같은 그룹 안의 가장 큰 하위 번호 다음 번호를 사용한다.
- 기존 넓은 문서를 세부 문서로 분리할 때는 원문을 삭제하지 말고 `Superseded`로 바꾸고, 대체된 세부 문서 링크만 남긴다.
- README에는 Superseded 문서와 활성 세부 문서를 모두 표시하되, 활성 문서는 그룹 번호 순서로 정렬한다.

## 대안 및 예외 흐름 번호 규칙

- 각 대안 또는 예외 흐름에 관련 기본 흐름 번호와 영문 소문자를 조합한 식별자를 붙인다. 예: `1a`, `1b`, `4a`.
- 같은 기본 흐름에 연결된 항목은 `a`, `b`, `c` 순서로 작성한다.
- 기본 흐름에서 처음 벗어나는 단계의 번호를 사용한다.
- 여러 기본 흐름 단계에 걸친 예외는 가장 이른 관련 단계에 연결하고 본문에 적용 범위를 명시한다.
- 기본 흐름 번호를 변경하면 연결된 대안 및 예외 흐름 번호도 함께 변경한다.
- 관련 기본 흐름 번호 없이 대안 또는 예외 흐름을 작성하지 않는다. 항목이 없으면 `- 없음`으로 기록한다.

## 상태 규칙

- `Proposed`: 문서화됐지만 구현을 시작하지 않은 상태다.
- `In Progress`: 구현을 진행 중이거나 완료되지 않은 상태다.
- `Implemented`: 요청한 동작을 구현했지만 충분히 검증하지 않은 상태다.
- `Verified`: 관련 자동화 테스트 또는 직접 실행 검증을 통과한 상태다.
- `Superseded`: 다른 유스케이스로 대체된 상태다. 대체 문서를 연결한다.

코드만 검토한 결과로 `Verified` 상태를 지정하지 않는다.

## 문서화 규칙

- 사용자가 의도한 동작을 보존하고 확인되지 않은 비즈니스 규칙을 만들지 않는다.
- 구현을 막지 않는 불명확한 내용은 미결 질문에 `TBD`로 기록한다. 구현 방향을 크게 바꾸는 내용만 사용자에게 질문한다.
- 인수 조건은 관찰하고 검증할 수 있게 작성한다.
- 대안 및 예외 흐름 번호가 기본 흐름과 정확히 연결되는지 검토한다.
- 코드 변경 전후에 관련 유스케이스를 다시 확인하고, 동작·설정·예외·인수 조건·구현 상태의 변화를 사용자 요청 없이도 같은 작업 차례에 반영한다.
- 확인된 파일 경로, 결정 사항, 테스트 결과와 제한 사항만 구현 메모에 기록한다.
- 기존 유스케이스를 삭제하지 않는다. 더 이상 유효하지 않으면 `Superseded`로 표시한다.
- 사용자가 문서화만 요청했다면 코드 변경 권한까지 부여한 것으로 해석하지 않는다.
- 구현된 유스케이스의 요구사항이 변경되면, 변경 동작이 이미 검증된 경우가 아닌 한 상태를 `Proposed` 또는 `In Progress`로 낮춘다.
